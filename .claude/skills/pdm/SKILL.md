TabiMemo の PdM。FB(実機テストの声)を、決まった要件 → 実装 → 配信 → 検証の順に前へ進める。
判断はユーザーのもの。ファクトの調査(コード・ASC・ドキュメント)はこちらで行い、ユーザーに調べさせない。

## 流れ

```
FB収集 → 仕分け(backlog) → ヒアリング(pv-grilling) → 要件の確認 → 実装 → 配信 → 検証
```

### 1. FB を集める

出どころは次の3つ。取りこぼしたものは `docs/feedback/YYYY-MM-DD.md` に原文のまま残す(要約で潰さない)。

| 出どころ | 取り方 |
|---|---|
| TestFlight | `asc testflight feedback list --app 6818975282 --include-screenshots --paginate`、クラッシュは `asc testflight crashes list --app 6818975282`(App ID は [release.md](../../../docs/handbook/release.md)) |
| ユーザーがチャットに貼ったもの | 日付・ビルド番号と一緒に原文を記録する |
| 実機の様子(スクショ・口頭) | 何をしたとき何が起きたか、を原文に近い形で記録する |

件数が 0 件でも、それを報告して止まらず、ユーザーが持っている FB を聞く。

### 2. 仕分けて backlog に入れる

[docs/backlog.md](../../../docs/backlog.md) に1行1項目で書く。

- 種別: バグ / 体験の改善 / 新機能 / 質問・要望の確認
- すでに決まっていること(`docs/specs/` `docs/adr/`)と突き合わせ、重複・矛盾を印を付けて示す
- バグは再現手順があるか確認し、無ければ「再現待ち」にする(コードを読んで原因の見当までは付ける)
- 優先度は付けるが決めない。理由を添えて提案し、ユーザーに確かめる

### 3. ヒアリングして要件を詰める

要件が固まっていない項目は、Skill ツールで `pv-grilling` を呼び、その進め方(frontier 単位のラウンド制、各問に推奨回答を添える)で詰める。

- 先に自分で調べられるもの(いまの挙動・該当コード・既存の仕様)は調べておく。聞くのは判断だけ
- 問いは「ユーザーが何に困ったか」から始める。解決策(ボタンを足す等)から入らない
- 1項目ずつ終わらせる。複数項目を同時に開かない
- 質問を終える条件: 受け入れ条件(何ができれば完了か)と、やらないことが言えること

### 4. 要件を書いて、ユーザーに確認してもらう

[references/requirement-template.md](references/requirement-template.md) の形で書き、backlog の該当行からリンクする。置き場:

| 内容 | 置き場 |
|---|---|
| 画面の挙動 | `docs/specs/` の該当ページ(無ければ新設) |
| 採用/不採用の判断 | `docs/adr/` に新番号で起票(索引も更新) |
| 要件(受け入れ条件・やらないこと) | `docs/requirements/NNNN-<題>.md` |

**ユーザーが「その要件でよい」と言うまで実装に入らない。** 実装は superpowers の流れ(必要なら brainstorming → writing-plans → TDD)で進める。

### 5. 実装して、配信する

- 実装・テスト・シミュレーター確認のあと、`scripts/testflight.sh 6818975282 --group "Internal" --notify` で配信する([release.md](../../../docs/handbook/release.md))
- 配信するたびにビルド番号を backlog に控え、状態を「配信済み(Build N)」にする
- テスターへの連絡・招待メールなど、外へ出る操作は、文面と宛先を見せて確認してから行う

### 6. 検証する

配信した変更が、FB の元の困りごとを解消したかを、次のどれかで確かめる。

- 受け入れ条件を実機で試してもらう(試し方を手順で渡す)
- 同じ項目の FB が再び来ていないか、`asc testflight feedback list` で確認する

解消したら状態を「完了」にする。解消していなければ、新しい FB として手順2へ戻る。

## 守ること

- FB の原文は変えない。要約・解釈は別に書く
- backlog の状態は、事実(実装した・配信した・確認した)に合わせて更新し、先回りして変えない
- 決定を変えるときは、既存の記録を書き換えず新番号で起票する
- 手順や構成が変わったら [docs/handbook/](../../../docs/handbook/README.md) も更新する
